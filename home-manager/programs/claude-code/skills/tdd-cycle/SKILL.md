# TDD サイクル

## 原則

- **テストは "what"**: 期待される振る舞いを表現する
- **実装は "how"**: その振る舞いをどう実現するかを書く
- **コミットメッセージは "why"**: なぜその変更を行うかを残す
- 1 サイクル = 1 単機能 (最小粒度)。仕様を分解してから着手する

## サイクル

1. **仕様分解**: 受け取った仕様を独立した単機能に分ける。依存順に並べ、最初に着手するものを 1 つ選ぶ
2. **Red**: 着手対象の振る舞いを検証する失敗するテストを 1 つ書く
3. **実行**: テストが "期待通りに失敗" することを確認する (実装未着手でテストが通ったらテストが誤っている)
4. **Green**: 最小限のコードでテストを緑にする。この段階では最適化・抽象化しない
5. **Refactor**: 緑を維持したままコードを整理する。重複除去、命名改善、意図の明確化
6. **Type/Check**: 静的型検査・コンパイル検査がある言語では実行する (Python: mypy / pyrefly、Rust: cargo check、TypeScript: tsc --noEmit。Go は go test がコンパイルを内包するため独立ステップ不要)。失敗したら Refactor に戻る
7. **Lint**: 言語固有スキル (lang-go / lang-typescript / lang-python / lang-rust) のリンタコマンドを実行。失敗したら Refactor に戻る
8. **Format**: 言語固有スキルのフォーマッタを適用。Lint と Format が単一コマンドの言語 (TypeScript の `biome check --write .` 等) では 7–8 を 1 ステップに統合してよい
9. **次サイクル**: 全テストが緑なら、次の単機能へ

## ガード

- サイクル途中で別機能の実装・リファクタに寄り道しない
- 1 サイクル完了前にコミットを作らない (中途半端な状態を残さない)
- テストが緑にならないまま他の変更に進まない
- 全サイクル完了後、全体を通しで実行してリグレッションがないことを確認する
- プロジェクトの CLAUDE.md・規約がサイクルの一部省略や変更を指示している場合はプロジェクト規約を優先する (例: 採点系リポジトリの規約により Claude がテスト実行を行わない運用)

# 品質パイプライン (完了前に必ず通す)

## 実行順

1. **テスト**: 全テストを実行し、緑であることを確認
2. **Type/Check**: 静的型検査・コンパイル検査がある言語では実行する (コマンドは lang-* スキルを参照)
3. **Lint**: 静的解析を実行。警告・エラーはゼロにする
4. **Format**: 自動フォーマッタを適用し、差分があれば保存
5. **再テスト**: Format により意図せず壊れることがないかを検証

## 失敗時の扱い

- **テスト失敗**: 直ちに TDD サイクルの Red フェーズに戻る。失敗テストを特定し、原因を修正してから再実行
- **Lint 警告**: 修正できるものは修正、意図的な例外は理由コメントで明示 (Code comments explain "why not")
- **Format 差分**: そのまま適用。手動整形で無駄に戦わない

## 禁止事項

- テストをスキップ・無効化して通す (例: `xit`, `t.Skip`, `@pytest.mark.skip`) — 理由を明記した一時的なもののみ許容し、次サイクルで解消
- Lint ルールの広域無効化 (`// eslint-disable-next-line` のような局所的な例外のみ許容)
- Format の部分的無効化
- pre-commit / CI フック回避 (`--no-verify`)

## 完了判定

全仕様でテストが緑、型検査 (該当言語のみ) と Lint がクリーン、Format 適用済みの状態を "実装完了" とみなす。完了宣言の前に review-checklist スキルでセルフレビューを行う。
